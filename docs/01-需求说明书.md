## 一、项目背景与目标

### 1.1 背景

传统中小电商企业在没有统一系统时，商品维护、订单发货、售后处理、营销投放通常分散在 Excel、聊天工具与多个表格中，导致：

- 商品多规格（颜色 + 尺码 + 存储）难以维护，价格与库存容易失真；
- 下单与库存不同步，超卖与漏发时有发生；
- 售后无工单留痕，责任无法追溯；
- 管理员权限无边界，客服可以看到系统配置，仓储可以去改优惠券；
- 运营缺少数据支撑，无法判断哪个类目、哪个商品真正赚钱。

### 1.2 目标

建设一套**前后端分离的 B2C 电商管理系统**，在同一套代码库中同时提供：

1. **买家商城前台**（`/`）：浏览 → 加购 → 结算 → 支付 → 收货 → 评价 → 售后的完整闭环；
2. **管理后台**（`/admin`）：商品、订单、售后、营销、会员、系统六大模块的运营支撑；
3. **可落地的权限体系**：三级角色 + 65 条权限标识，前端动态菜单/按钮 + 后端方法级 `@PreAuthorize` 双层校验。

## 二、系统定位

### 2.1 定位

**B2C 单商户自营商城 + 内部管理后台**。

- 商品的**卖方是平台自己**（无第三方商家入驻、无店铺维度、无结算分账）；
- 买家侧是**零售**场景（单笔订单以一个收货地址为界，无双地址拆单）；
- 支付为**模拟支付**（`pay_type=1`，无第三方支付通道对接），适合教学、演示与内网业务系统；
- 内容域（轮播图 / 公告 / 优惠券）由平台运营统一维护。

### 2.2 边界（明确不做的部分）

| 不做 | 说明 |
| --- | --- |
| 真实支付/退款通道 | 点击"模拟支付"直接将订单置为待发货；退款为状态流转 + 库存回补，不产生真实资金流水 |
| 商家入驻 / 多店铺 | `product` 无 `shop_id`，`sys_role` 只有 ADMIN/OPERATOR/WAREHOUSE |
| 分布式事务 / 消息队列 | 库存扣减依赖数据库行锁与原子 UPDATE，下单在单库事务内完成 |
| 秒杀 / 拼团 / 分销 | `coupon` 之外的营销玩法未实现，`sys_config` 中亦无相关开关 |
| 移动端 App / 小程序 | 仅 Web（Vue3 SPA），未做响应式小程序适配层 |
| 消息通知（短信/邮件/站内信） | 无相关表与接口，`notice` 为运营公告而非用户消息 |


### 3.4 权限校验的"两层"结构

| 层 | 位置 | 判定内容 | 失败响应 |
| --- | --- | --- | --- |
| 第一层（粗） | `SecurityConfig` | 路径前缀判定用户类型：`/api/admin/**` 需 `TYPE_ADMIN`；其余受保护接口需 `TYPE_BUYER` | 401（未登录）/ 403（类型不符） |
| 第二层（细） | `@PreAuthorize` 方法注解 | 具体业务权限标识，如 `hasAuthority('product:add')` | 403 |
| 前端配合 | 路由 `meta.perm` + `v-perm` 指令 | 隐藏无权限的菜单与按钮（**仅体验优化，不作为安全边界**） | 跳回 `/admin/dashboard` + 提示 |

**校验顺序陷阱**：由于第一层按路径前缀先判 `TYPE_ADMIN`，因此**买家 Token 调用 `/api/admin/**` 会得到 403 而不是 401**；而完全不带 Token 时，Spring Security 的 `authenticationEntryPoint` 返回 401。

### 3.5 前端按钮级权限指令

```js
// frontend/src/directives/permission.js
// v-perm="'product:add'"            单个权限
// v-perm="['product:add','product:edit']"  任一满足即可
// v-perm:buyer="'buyer:login'"      买家登录态
```

指令在 `mounted` 阶段判断，不允许时**直接把 DOM 节点从父节点移除**（而非 `display:none`），因此无法通过开发者工具"取消隐藏"来误用——当然，真正的安全仍由后端 `@PreAuthorize` 保证。

| 名称 | 买家注册 |

#### FR-ORD-02 提交订单

| 项 | 内容 |
| --- | --- |
| 名称 | 提交订单（扣库存 + 核销券 + 清购物车） |
| 参与角色 | 买家 |
| 前置条件 | 预览通过；收货地址属于本人 |
| 主流程 | 1. `POST /api/order/submit`（`{addressId, cartIds/buyNow, userCouponId, remark}`）<br>2. 校验地址存在且属于当前用户<br>3. **服务端重新校验并重算全部金额**（不信任前端传入）<br>4. 生成订单号 `MO + yyyyMMddHHmmss + 4位随机数`（最多重试 10 次防重）<br>5. 写 `orders` 主表（状态 0 待付款；收货人/电话/地址**快照**）<br>6. 逐条写 `order_item`（商品名/图/规格/单价**快照**，`is_commented=0`）<br>7. 逐条**原子扣减 SKU 库存并累加销量**，同步商品维度总库存与销量<br>8. 核销优惠券（`user_coupon.status=1` + `order_id` + `use_time`，`coupon.used_count + 1`）<br>9. 删除已下单的购物车条目<br>10. 返回 `{orderId, orderNo, payAmount}` |
| 异常/分支 | ① 地址不存在或非本人 → 600「收货地址不存在或无权使用」<br>② 地址必填校验 → 400「请选择收货地址」<br>③ 任一 SKU 并发下被抢空（原子 UPDATE 影响 0 行）→ 600「库存不足：X」并**整体事务回滚**<br>④ 其余同预览的券与商品校验 |
| 后置条件 | `orders` + N 条 `order_item` 新增；SKU/商品库存减少、销量增加；券转为已使用；对应购物车条目删除。全部在**同一个 `@Transactional(rollbackFor = Exception.class)`** 内，任一失败全部回滚 |

**库存扣减的原子 SQL（关键实现）**：

```java
int rows = productSkuMapper.update(null, Wrappers.<ProductSku>lambdaUpdate()
        .setSql("stock = stock - " + qty)
        .setSql("sales = sales + " + qty)
        .eq(ProductSku::getId, item.getSku().getId())
        .ge(ProductSku::getStock, qty));       // ← 条件扣减：库存不足则影响 0 行
if (rows == 0) {
    throw new BusinessException("库存不足：" + item.getProduct().getName());
}
// 商品维度同步（带下界保护）
productMapper.update(null, Wrappers.<Product>lambdaUpdate()
        .setSql("stock = GREATEST(stock - " + qty + ", 0)")
        .setSql("sales = sales + " + qty)
        .eq(Product::getId, item.getProduct().getId()));
```

> `WHERE id = ? AND stock >= qty` 把"判断 + 扣减"合并为一条 UPDATE，由 InnoDB 行锁保证原子性，无需 `SELECT ... FOR UPDATE` 悲观锁，也不存在"读-改-写"竞态导致的超卖。

**审核结果对库存与订单的影响**：

| 分支 | 售后状态 | 库存 | 订单最终状态 |
| --- | --- | --- | --- |
| 同意 · type=1 仅退款 | 4 退款完成 | **不回补**（仅退款不涉及退货入库） | 退款额 ≥ 实付 → 4 已取消；否则 → 3 已完成 |
| 同意 · type=2/3 | 3 待买家退货 | 不回补 | 保持 5 售后中 |
| 拒绝（当前 0 或 3） | 2 已拒绝 | 不回补 | 已收货 → 3；否则 → 2 |
| 退款完成（当前 0/1/3） | 4 退款完成 | **回补**（单品回补该明细，整单回补全部明细） | 退款额 ≥ 实付 → 4 已取消；否则 → 3 已完成 |

```java
// 退款完成后的订单终态（RefundServiceImpl.settleOrderAfterRefund）
Integer finalStatus = (refundAmount.compareTo(payAmount) >= 0)
        ? OrderStatus.CANCELLED.getCode()   // 4
        : OrderStatus.FINISHED.getCode();   // 3
```

> **注意**："仅退款"在同意时即视为完成，**不回补库存**——因为商品并未退回。只有走到"退款完成"（通常对应退货退款/换货）才执行入库回补。这是退款与退货在库存语义上的关键区别。

| 主流程 | **① 导出** `GET /api/admin/products/export`：复用列表查询条件，按 `id ASC` 最多 **5000** 条，表头为「商品ID/商品名称/分类/品牌/价格/原价/总库存/销量/状态/是否推荐/创建时间」，文件名 `商品列表_yyyyMMddHHmmss`<br>**② 模板** `GET /api/admin/products/template`：表头「商品名称/副标题/品牌/分类名称/单位/SKU规格(如 颜色:红色;尺码:M)/SKU价格/SKU原价/SKU库存/SKU编码」+ 8 条填写说明<br>**③ 导入** `POST /api/admin/products/import`（multipart `file`） |
| 异常/分支 | **导出**：无。<br>**导入**：① 文件为空 → 600「请选择要导入的 Excel 文件」<br>② 非 `.xlsx`/`.xls` → 600「仅支持 .xlsx / .xls 格式的 Excel 文件」<br>③ 无工作表 → 600「Excel 文件中没有工作表」<br>④ 解析失败 → 600「Excel 解析失败：X」<br>⑤ 无有效数据 → 600「Excel 中没有可导入的数据，请使用「下载模板」获取标准模板」<br>⑥ 商品名称为空的行 → 计入失败并记录"第 N 行：商品名称不能为空"<br>⑦ 价格/库存非数字 → 记录"第 N 行：SKU价格「X」不是合法的数字"等<br>⑧ 规格格式错 → "SKU规格「X」格式错误，应为 规格名:规格值"<br>⑨ 分类不存在 → "商品「X」（第 N 行起）导入失败：分类「Y」不存在"<br>⑩ 超过 5000 行 → 提示"单次最多导入 5000 行，超出的行已忽略" |

**导入的关键约定（来自模板说明原文）**：

1. 同一商品名称填写多行 → 合并为一个 SPU，每行一个 SKU；
2. 商品名称必填；
3. 分类名称必须与系统已有分类**完全一致**；
4. 规格格式 `规格名:规格值`，多规格用英文分号 `;` 分隔（代码兼容中文分号 `；` 与全角冒号 `：`）；
5. 价格/原价/库存必须为数字，库存为不小于 0 的整数；
6. SKU 编码可留空；
7. 导入成功的商品默认**上架**，单位默认「件」，不推荐、非新品、非热销；
8. 单行错误只影响该商品。

> **实现细节**：导入时按"商品名称"分组（`LinkedHashMap` 保持模板顺序），每组的规格定义由各行 `specMap` 按出现顺序合并（`LinkedHashSet` 去重）。

#### FR-MEM-01 会员列表与消费统计

| 项 | 内容 |
| --- | --- |
| 名称 | 会员分页（含下单数与消费总额） |
| 参与角色 | ADMIN、OPERATOR（`member:list`） |
| 前置条件 | 无 |
| 主流程 | 1. `GET /api/admin/users?keyword=&status=&page=&size=`<br>2. `keyword` 模糊匹配 `username` / `nickname` / `phone`<br>3. 按 `create_time DESC, id DESC` 分页（MyBatis-Plus 自动追加 `deleted=0`）<br>4. **一次性**用一条 SQL 统计当前页所有会员的订单数与消费金额（`GROUP BY user_id`），避免 N+1<br>5. 返回含 `orderCount`、`totalConsumption` |
| 异常/分支 | 参数非法 → 400 |

**统计 SQL（由 QueryWrapper 生成）**：

```sql
SELECT user_id, COUNT(*) AS cnt, COALESCE(SUM(pay_amount), 0) AS amount
FROM orders
WHERE deleted = 0 AND user_id IN (...) AND status IN (1, 2, 3, 5)
GROUP BY user_id
```

> **注意**：该 SQL 由框架拼装，**不会自动追加 `deleted = 0`**（因为用了 `selectMaps` + 原生 `QueryWrapper`，MyBatis-Plus 的逻辑删除只对实体查询生效）。为弥补这一点，`query()` 首页查询走的是 `userMapper.selectPage`（会追加 `deleted=0`），因此已删除会员不会出现在列表中，其统计数据也不会被读取。这一点在代码注释中未显式说明，属于需要留意的实现细节。

| NFR-P-06 | Redis 连接池 | Lettuce：`max-active=16`、`max-idle=8`、`min-idle=2`、`max-wait=3000ms` |
| NFR-P-07 | 大批量导出不拖垮数据库 | 订单导出循环翻页，每批 200 条，上限 5000；商品导出 `LIMIT 5000` |

### 5.2 安全

| 编号 | 需求 | 实现依据 |
| --- | --- | --- |
| NFR-S-01 | 密码不得明文存储 | 全量使用 `BCryptPasswordEncoder`（`SecurityConfig#passwordEncoder`），登录/注册/改密/重置密码均走 `encode`/`matches` |
| NFR-S-02 | 登录态可主动失效 | JWT 签名 + Redis 存储 `LoginUser`（含当前有效 token），请求时比对 token 字符串；退出/禁用/删号/改角色/重置密码均删除 Redis 键 |
| NFR-S-03 | Token 有明确有效期 | `mall.jwt.expire = 604800` 秒（7 天），Redis TTL 与之对齐 |
| NFR-S-04 | 双层权限校验 | `SecurityConfig` 路径级（TYPE_ADMIN/TYPE_BUYER）+ `@PreAuthorize` 方法级权限标识 |
| NFR-S-05 | 无状态会话 | `SessionCreationPolicy.STATELESS`，禁用 CSRF / formLogin / httpBasic / logout |
| NFR-S-06 | 参数校验 | 42 个 DTO 使用 `jakarta.validation` 注解，Controller 层 `@Valid`；全局异常处理器统一转 400 并聚合多条错误信息 |
| NFR-S-07 | SQL 注入防护 | 全部使用 MyBatis-Plus 条件构造器或 `#{}` 占位符；未发现字符串拼接 SQL（唯一动态拼接的是 `setSql("stock = stock - " + qty)`，其中 `qty` 为**已校验的正整数**，且 `specInfo` 等用户输入从不进入 SQL 片段） |
| NFR-S-08 | 目录穿越防护 | 上传与删除均 `normalize()` 后校验 `startsWith(root)`；扩展名白名单 `jpg,jpeg,png,gif,bmp,webp,svg` |
| NFR-S-09 | 文件大小限制 | 单文件 10MB（`MAX_FILE_SIZE` + `spring.servlet.multipart.max-file-size`），单请求 50MB |
| NFR-S-10 | 越权防护 | 所有买家侧"按 ID 操作"的接口都校验 `user_id` 归属（订单、地址、购物车、售后、收藏、评价） |
| NFR-S-11 | 账号枚举防护 | 登录失败统一提示「用户名或密码错误」，不区分用户是否存在 |
| NFR-S-12 | 内建账号保护 | ID=1 的超级管理员禁止删除/禁用；禁止删除或禁用当前登录管理员 |
| NFR-S-13 | 逻辑删除 | 8 张表使用 `deleted` 字段（`user`、`user_address`、`category`、`product`、`orders`、`coupon`、`banner`、`notice`、`sys_user`），查询自动过滤 |
| NFR-S-14 | 跨域控制 | CORS 允许全部来源模式（`*`）、全部方法（GET/POST/PUT/DELETE/OPTIONS/PATCH）、全部请求头，暴露 `Content-Disposition`，`allowCredentials=true`，预检缓存 3600 秒 |

> **NFR-S-14 的风险提示**：`allowedOriginPatterns("*")` + `allowCredentials(true)` 在生产环境属于宽松配置。当前设计意图是便于本地联调（前端 dev server 代理 + 直连），生产部署时应收敛为具体域名白名单。

## 六、业务规则汇总

数值与规则均从代码常量或 `sys_config` 种子数据核对得出。

| 编号 | 规则 | 取值/逻辑 | 代码位置 |
| --- | --- | --- | --- |
| **BR-01** | 包邮门槛与运费 | 商品总额 ≥ **99.00** 元免运费，否则收 **10.00** 元 | `freeFreightAmount=99.00`、`freightFee=10.00` |
| **BR-02** | 实付金额下限 | `payAmount = max(商品总额 + 运费 − 优惠, 0.01)`，恒不小于 **0.01** 元 | `MIN_PAY_AMOUNT = 0.01` |
| **BR-03** | 折扣券优惠上限 | 折扣券优惠金额最高 **100.00** 元；折扣率非法（≤0 或 ≥10）时优惠为 0 | `MAX_DISCOUNT_AMOUNT = 100.00` |
| **BR-04** | 优惠金额上限 | 任何优惠券的抵扣金额**不超过商品总额**（超出则按商品总额计） | `calcDiscount` 末段 |
| **BR-05** | 下单即扣库存 | 提交订单时立即原子扣减 SKU 库存并累加销量；商品维度总库存同步减少 | `deductStock` |
| **BR-06** | 库存扣减原子性 | `UPDATE product_sku SET stock=stock-?, sales=sales+? WHERE id=? AND stock>=?`，影响 0 行即抛异常回滚 | `deductStock` |
| **BR-07** | 库存下界保护 | 商品维度用 `GREATEST(stock - ?, 0)`；回补销量用 `GREATEST(sales - ?, 0)` | `deductStock` / `restoreStock` |
| **BR-08** | 取消订单回滚 | 取消（买家）或关闭（管理端）待付款订单时：回补 SKU 与商品库存、回退销量、退还优惠券 | `cancelInternal` |
| **BR-09** | 优惠券回滚幂等 | 退券前校验 `user_coupon.status=1`，非已使用状态直接返回；`used_count` 用 `GREATEST(...,0)` | `returnCoupon` |
| **BR-10** | 未支付自动取消 | 创建后超过 **30 分钟**未支付的订单自动取消（`order-auto-cancel-minutes=30`），在买家查询订单时惰性触发 | `autoCancelExpiredOrders` |
| **BR-11** | 每人限领张数 | 取 `coupon.per_limit`（最小 1）；已领数 ≥ 限领数时拒绝 | `receiveCoupon` |
| **BR-12** | 券总量限制 | `received_count >= total_count` 时提示"已被领完" | `receiveCoupon` |
| **BR-13** | 用户券有效期 | `user_coupon.expire_time` 优先取券的 `end_time`；券无结束时间时取领取时间 + **30 天** | `receiveCoupon` |
| **BR-14** | 券适用范围 | `scope=1` 全场；`scope=2` 指定分类（**二级分类命中其一级分类同样可用**）；`scope=3` 指定商品（任一商品命中即可）。`scope_ids` 为空时视为全场 | `scopeMatched` |
| **BR-15** | 券使用门槛 | `商品总额 >= coupon.min_amount` 才可用 | `requireAvailableCoupon` |
| **BR-16** | 券有效性 | 券需 `status=1`、`start_time <= now <= end_time`，用户券需 `status=0` 且未过期 | `requireAvailableCoupon` |

| **BR-18** | 券发行量保护 | 编辑时 `total_count` 不得小于 `received_count` | `CouponServiceImpl.save` |
| **BR-19** | 折扣率范围 | 折扣券折扣率（如 8.5 表示 8.5 折）必须在 **0.1 ~ 9.9** 之间 | `DISCOUNT_MIN/MAX` |
| **BR-20** | 券状态归一 | 用户券 `status=0` 且 `expire_time < now` 时，对外展示为 `status=2 已过期` | `toUserCouponVO` |
| **BR-21** | 订单状态机 | `0 待付款 → 1 待发货 → 2 待收货 → 3 已完成`；旁支 `4 已取消`、`5 售后中` | `OrderStatus` |
